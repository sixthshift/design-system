# 06 — Reconsider shipping a CHANGELOG

**Effort:** S · **Risk:** low · **Decision item, not just a task**

## Problem

There is no `CHANGELOG.md`, and this is a deliberate, documented choice:

> No release pull request and no changelog: the tag range is the record.

That reasoning holds well for a personal system with one author. It holds less
well for something published to npm with provenance, versioned by semver, and
consumed as a dependency. A consumer looking at `0.4.0 → 0.5.0` in their
`package.json` has no way to learn what changed without cloning the repo and
walking `git log` between two tags — and the breaking changes are exactly the
ones they need to see, since below `1.0.0` a breaking change moves the *minor*
rather than the major.

Recent history contains at least two changes a consumer would want flagged:

```
1be95c3 refactor(theme)!: rename the size and intent vocabularies
1f4a2d0 fix(radio-button)!: a selected radio stays selected
8f9f5d2 feat(pickers): make every date/time picker typeable, and prune the library
```

"Pruned the library" and "renamed the size and intent vocabularies" are the kind
of thing that breaks a consumer's build. Under the current scheme they are
discoverable only by archaeology.

## The decision

This is a genuine trade-off, not an oversight to fix. Consider:

**Keep no changelog if:** the package stays effectively single-consumer, and the
maintenance cost of a generated file (merge conflicts, noise commits) outweighs
the benefit.

**Add one if:** you intend the package to be adopted more widely, or you're
heading toward 1.0. At 1.0 the absence becomes conspicuous — it is the first
thing a prospective consumer looks for.

Recommendation: **add it**, but generate it, never hand-write it. The commit
convention that already drives versioning carries everything needed.

## Approach (if adopting)

### 1. Generate from the same source of truth

`scripts/next-version.ts` already walks commits since the last `v*` tag and
classifies them by Conventional Commit prefix. Reuse that walk — do not add a
second, differently-behaving parser. Extend it with a `--changelog` mode that
emits Markdown for the current tag range.

Grouping should mirror the bump table already in the README:

- **Breaking** — `!` or `BREAKING CHANGE:` footer (call these out first and
  loudly; below 1.0 they hide in minor bumps)
- **Features** — `feat:`
- **Fixes** — `fix:`, `perf:`
- **Internal** — `refactor:`, `build:`, `revert:`, unrecognised subjects

`chore:`/`ci:`/`docs:`/`style:`/`test:` cut no release and should not appear.

### 2. Where it gets written

The release is fully automatic and unattended: CI green → `version.yml` writes
the version, commits `chore(release): vX.Y.Z [skip ci]`, tags, publishes. The
changelog entry should be written in that **same** commit, so the file and the
tag never disagree.

Do not introduce a release-PR flow to accommodate this. The current pipeline's
main virtue is that it has no human step, and the README is explicit that
`version.yml` must remain the sole entry point for the OIDC trusted-publishing
claim to match. Appending to a file inside the existing commit changes nothing
about that.

### 3. Alternative if you'd rather not

GitHub Releases with auto-generated notes gives most of the benefit and touches
no file in the repo. `version.yml` already creates the tag; adding a release with
`gh release create --generate-notes` is a few lines. Consumers get a browsable
history; the repo stays free of a generated file. Weaker than a changelog (not
visible from the npm page or the tarball) but nearly free.

## Acceptance criteria

- [ ] Decision recorded — either "no changelog, because …" written into the README's Versioning section, or the file exists
- [ ] If adopting: generated by `scripts/next-version.ts`, not hand-maintained
- [ ] If adopting: breaking changes appear in their own section at the top of each entry
- [ ] If adopting: written in the same `chore(release):` commit that tags the version
- [ ] `version.yml` remains the sole workflow entry point (OIDC constraint)

## Notes

- Whichever way this goes, the README's Versioning section should state the
  decision. Right now the absence reads as an omission; one sentence turns it
  into a position.
