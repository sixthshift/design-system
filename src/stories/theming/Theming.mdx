# Theming

</div>

Semantic tokens are the theming surface. Each one names **a meaning, not a
colour** — `--bg-danger`, not `--bg-red` — and carries one value per mode.
Components read them, your markup reads them, and re-declaring one re-skins
every surface that means the same thing.

```css
@import "tailwindcss";
@import "@sixthshift/design-system/themes/linen.css";   /* the tokens + their utilities */
@source "../node_modules/@sixthshift/design-system";
```

`@source` is required — Tailwind 4 never scans `node_modules`, and without it
every component renders unstyled.

## Build a token name

Names are assembled left to right, and you stop as soon as you have said enough:
`--bg-danger` is a complete name, and most tokens use neither of the last two
slots.

<TokenBuilder />

A ✕ marks an option that would name something the stylesheet does not declare.
Those gaps are the convention, not an oversight — the clearest one being that
`normal`, `subtle` and `strong` take no weight, because **they are the weight**.
They are one grey scale, so `--bg-subtle-strong` asks for two positions at once.
The four intents that carry meaning are a hue, and the weight says how loud to
be within it.

## `fg` versus `fg-on`

The one distinction the builder cannot teach you, because both names are real.
`--fg-danger` is danger-coloured text on an **ordinary** surface;
`--fg-on-danger` is the text that goes **on top of** `--bg-danger`.

<PairingDemo />

The rule: if the element behind your text is painted with `--bg-{intent}`, the
text is `--fg-on-{intent}`. Otherwise it is `--fg-{intent}`. Weight travels with
the pair — `--bg-danger-subtle` wants `--fg-on-danger-subtle`.

Every `fg-on-*` pairing the library ships is verified at 4.5:1 by
`bun run check:contrast`. The two halves of a mismatched pair are not, because
they were never meant to meet.

## Using them

Two ways in, resolving to the same variable:

```tsx
<aside className="bg-bg-danger-subtle text-fg-on-danger-subtle border border-border-danger">
```

```css
.receipt-total { color: var(--fg-danger); }
```

The utilities exist because each token has a matching `@theme` entry
(`--color-bg-danger: var(--bg-danger)` is what makes `bg-bg-danger` compile).
That block also sets `--color-*: initial`, dropping Tailwind's stock colours, so
`bg-red-500` does not compile in your own markup either. Re-declare any you want
back in your own `@theme` after the import.

Non-colour tokens work the same way:

| Tokens | Utility | Values |
| --- | --- | --- |
| `--z-index-*` | `z-modal` | `content-sticky` 10 · `app-bar` 30 · `sheet` 50 · `popover` 60 · `modal` 70 · `toast` 9999 |
| `--animate-*` | `animate-fade-in` | `fade-in/out`, `fade-in/out-slow`, `slide-{up,right,left}-in/out` |
| `--font-sans`, `--font-mono` | `font-sans` | Inter Variable, JetBrains Mono Variable |

One token sits outside the naming convention entirely: `--focus-ring`.

## Light and dark

This layer is where the two modes live: same names, two blocks, and nothing
downstream has to know a mode exists.

```css
:root:not([data-theme]),
:root[data-theme="light"] { --bg-danger: #9e2533; }
:root[data-theme="dark"]  { --bg-danger: #d55368; }
```

Mode is a `data-theme` attribute on `:root`, not `prefers-color-scheme`. The
`:not([data-theme])` half covers an app that has not set the attribute yet, and
declaring a token in one block only leaves it **undefined** in the other — no
error, no fallback.

Set the attribute however you like; the bundled hook is the short path:

```tsx
import { bootstrapTheme, useTheme } from "@sixthshift/design-system/hooks";

useEffect(() => bootstrapTheme(), []);            // once, at app bootstrap

const { theme, resolvedTheme, setTheme, toggleTheme } = useTheme();
// theme: "light" | "dark" | "system" — stored, syncs across tabs
// resolvedTheme: what "system" currently means right now
```

Because mode is an attribute, `dark:` in **your** markup also means
`[data-theme="dark"]` rather than the OS setting.

## Re-skinning

Redeclare the tokens, in both blocks, in your own stylesheet after the import.
Everything that means the same thing follows — no component knows it happened:

```css
:root:not([data-theme]),
:root[data-theme="light"] { --bg-brand: #6d28d9; --fg-on-brand: #ffffff; }
:root[data-theme="dark"]  { --bg-brand: #a78bfa; --fg-on-brand: #1a0b2e; }
```

Re-skin the whole family, not one token of it: `--bg-brand` without
`--bg-brand-hovered` gives you a button that snaps back to the old hue the
moment it is hovered. **[Theme](?path=/docs/design-system-theme--docs) emits the
whole family as CSS you can copy**, pre-filled with the shipped values — start
from that rather than assembling it from here. This is what one contains:

<FamilyAnatomy family="danger" />

**Adding a token of your own** — say a new `info` intent — takes the same two
blocks, plus an `@theme` entry if you also want the Tailwind utility:

```css
:root:not([data-theme]),
:root[data-theme="light"] { --bg-info: #034078; --fg-on-info: #ffffff; }
:root[data-theme="dark"]  { --bg-info: #6691c7; --fg-on-info: #06121f; }

@theme { --color-bg-info: var(--bg-info); }   /* only if you want `bg-bg-info` */
```

You own the contrast of anything you add or re-point: `bun run check:contrast`
only sees the pairings the library ships.

## More than one brand

There is one `brand` intent, and there stays one. A theme with several brand
colours — a primary plus a pastel per product line, say — names them, and an
element carrying `data-brand="<name>"` re-points every brand token inside it.
Every component under it that reads a brand token follows. The library never
learns the names.

```tsx
<Button intent="brand">Checkout</Button>                   // the theme's default brand
<Button intent="brand" brand="mint">Add to cart</Button>   // this button is mint
<article data-brand="lilac">…everything brand inside is lilac…</article>
```

`brand` is a plain string that renders as `data-brand`, the way `intent` renders
`data-intent`. The component does not check it; only your CSS gives a name
meaning. It is a prop on the components with an `intent` — Button, Toggle,
ToggleGroup (once, on the group), Badge, Message, Toast — and on the overlays.
Everything else that reads brand tokens (Checkbox, RadioButton, Switch, Tabs,
Select) follows a `data-brand` ancestor.

**Overlays carry the scope across their portal.** Popover, Tooltip, HoverCard,
Select and the pickers copy the brand around their trigger onto their own
element; Modal and Sheet copy it from whatever held focus when they opened. An
explicit `brand` on `Popover.Body`, `Tooltip.Body`, `HoverCard.Content`, `Modal`
or `Sheet` wins. A toast has no trigger, so it takes `brand` or nothing.

### The theme side

Two parts: one rule per brand binding its scale to generic `--brand-*` steps, and
inside each mode block, a nested rule per *kind* of brand mapping every brand
token onto those steps. In outline, with the default brand on `:root`:

```css
:root, [data-brand="periwinkle"] { --brand-50: …; …; --brand-950: …; }
[data-brand="mint"]              { --brand-50: …; …; --brand-950: …; }

:root:not([data-theme]),
:root[data-theme="light"] {
  --bg-normal: …;                                  /* the rest of the theme, unchanged */

  &, & [data-brand="periwinkle"] {                 /* the default brand */
    --bg-brand: var(--brand-500);
    /* …every brand token… */
  }
  & :is([data-brand="mint"], [data-brand="lilac"]) {   /* pastels, by name */
    --bg-brand: var(--brand-200);
    /* …every brand token… */
  }
}
/* …and the same nested rules inside the dark block. */
```

The four rules below each cost someone an afternoon:

1. **Declare the mapping on the scope selector, not only on `:root`.** A custom
   property that references another resolves on the element that declares it,
   and descendants inherit the resolved colour. `:root { --bg-brand:
   var(--brand-200) }` alone freezes to the root's brand: a `data-brand` further
   down changes `--brand-200` but not `--bg-brand`.
2. **The nearest `data-brand` wins, including the component's own.** The scale,
   the mapping and the recipe's `--button-bg: var(--bg-brand)` all land on the
   same element and resolve against each other. Nesting resets too: the default
   brand's name inside a pink card is the default again.
3. **Brands can need different step mappings.** A saturated primary and a pastel
   don't sit at the same lightness — the pastel's solid is a light step with dark
   text. Keep one mapping per kind; adding a brand is its scale rule plus its name
   in its kind's selector list.
4. **Select brands by name, never by bare `[data-brand]`.** "Any `data-brand`
   except the default" matches a typo or an empty value too, which then has no
   scale of its own and renders as something nobody defined. Listed by name, an
   unknown value matches nothing and inherits its surroundings exactly. That is
   why the component needs no validation.

Each mapping must cover the whole brand family — all of these, with every state
suffix:

`--focus-ring` is not in it, on purpose. The ring has to stand out from the
page, not from the brand, so it is one colour everywhere.

## The silent failures

None of these raise an error. Each just renders the wrong thing.

| Mistake | What happens |
| --- | --- |
| Token declared in one mode block only | Undefined in the other mode |
| New token with no `@theme` entry | `var(--bg-info)` works, the `bg-bg-info` utility never compiles |
| `--fg-danger` where `--fg-on-danger` belongs | Danger-on-danger. Legible in review, unreadable in production |
| Semantic re-skin wrapped in `@layer` | Loses. The library's `:root` token blocks are unlayered, and unlayered CSS beats every layer — so re-skins must stay unlayered. (Component-token overrides are the opposite: they belong in `@layer overrides`, which outranks the recipes.) |
| One token of a family re-skinned | The hover, pressed or disabled state snaps back to the old hue |
| Brand mapping declared only on `:root` | Every `data-brand` below it changes its scale but keeps the root's colours |
| Brand mapping selected by bare `[data-brand]` | A typo'd or empty name renders a colour nobody defined, instead of falling back |
